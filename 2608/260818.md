### [CS] 이벤트 버스 event bus
SW 용어로, 아래와 같은 구조를 가진 통신 패턴의 이름. 
* 누구든 버스에 이벤트를 publish할 수 있다
* 누구든 특정 이벤트를 subscribe할 수 있다
* 버스는 발행된 이벤트를 구독자에게 배달한다
* 발행자와 구독자는 서로를 모른다
* 버스는 이벤트의 내용이나 의미에 대해 아무것도 모른다

<br />

> ex. Redux로 비유하자면 dispatch(action)이 event publish, store.subscribe() / useSelector()가 event subscribe

### [Article] 상태 관리의 참담한 상태 The Absolute State of Management

우리는 흔히 "리액트는 애플리케이션의 상태를 관리한다"는 표현을 쓴다. 그런데 이 말이 맞다면 별도의 상태 관리 라이브러리는 필요없어야 하는데 `Redux`, `Zustand`, `Recoil`, `Jotai` ... 를 추가로 사용한다. 하지만 저자는 이 도구들 중 상태를 관리하는 건 하나도 없다고 주장한다. 이 라이브러리들은 물론 상태를 캡슐화하고, 상태 업데이트를 필터링하고, 변환하지만 상태를 `관리`한다고 보기는 어렵다는 것이다. 대신 상태 변경에 대한 알림을 `전파`하고, 경우에 따라 그 변경을 후처리하거나 캐싱한다.

이러한 동작들은 [이벤트 버스](260818.md#cs-이벤트-버스-event-bus)(발행-구독 Publish/Subscribe pattern)로 재현할 수 있다. 그러나 이벤트 버스는 "이 변경은 저 변경에 인과적으로 의존한다", "이 두 변경은 충돌했을 경우 이러한 병합 규칙을 따른다" ... 와 같은 규칙을 표현할 수단이 없다. 원문 예시는 아니지만 redux를 예로 들자면, redux는 state.count가 음수가 되면 안 된다는 것도, 늦게 도착한 서버 응답과 방금 사용자가 수정한 값 중 어느 쪽을 채택해야 하는지도 모른다. 이런 규칙은 우리가 reducer에 직접 써야한다. 

즉, 저자는 우리가 부르는 상태 관리 라이브러리들은 상태를 "관리"하는 brain이 아니라 상태 변경 소식을 "전파"하는 역할이라고 주장하고 있다.

<br />

### 상태 관리와 상태 전파(state propagation)는 다르다
상태를 관리한다는 것은 시간이 흐르면서 발생하는 변경을 올바르게 적용하고, 충돌을 적절히 해결하는 것.

실제 앱에서 상태 업데이트는 성격이 제각각이다
- 출처: 사용자 클릭, 스크롤, 서버 응답, 웹소켓 푸시, 타이머, 라우터 변경, ...
- 빈도: 폼 입력은 키 입력마다, 스크롤은 초당 수십 번, 서버 응답은 가끔, ...
- 범위: 버튼 / 섹션 / 화면 전체 / ...

그러나 이벤트 버스 입장에서는 전부 똑같은 이벤트 한 건. 어떤 업데이트가 어떤 것에 의존하는지, 어떤 순서로 처리되어야 하는지, 파급 범위가 어디까지인지 ... 에 대한 정보가 없다. 결국 버스 바깥에서 미들웨어, thunk/saga, 셀렉터 메모이제이션, 디바운싱, 수동 구독 최적화 등 상태 관리 코드로 부수적인 복잡성이 생긴다. 

예를 들면, 서버 응답이 늦게 도착했는데 사용자가 그 사이에 수정했다면 우리가 리듀서와 미들웨어에 부수적 코드로 로직을 보완해야한다. 이건 라이브러리가 관리하는게 아니라 결국 우리가 보완(관리)하는 것. 

직접 상태를 관리하는것에 가까운 라이브러리로는 Y.js를 예시로 들고있다. 내부에 벡터 클록 같은 순서, 인과 메타데이터를 가지고 있어서 CRDT 기반으로 실시간 동시편집할 때 시간과 인과, 충돌 관리를 해주는 진짜 상태 관리(!) 라이브러리이다.

### 💭

리액트의 useState도 Zustand의 store 구독도 Tanstack Query의 캐싱도 상태를 일시적이나마 담고 전달하고 캐싱하는 등 '다룬다'는 의미로는 "관리"에 해당되는거 아닌가? 싶었는데 번역 차이가 있는 것 같다. 한글 "관리"는 보관/유지/정돈 의 느낌인데, 영단어 management는 판단하고 중재하는 행위자의 뉘앙스이다. 

예를들면,
- memory manager : 누가 어떤 메모리를 받을지, 언제 회수할지 결정
- lock manager / transaction manager : 동시 요청의 순서와 격리를 중재
- window manager : 겹치는 창들의 배치와 포커스를 결정

위의 세 기능들은 요구들 사이에서 시스템이 직접 판정을 내린다. 이런 맥락에서 state management는 동시다발적인 상태 변경들의 순서와 충돌을 판정해주는 시스템이어야 한다는 주장이 이해가 간다... 하지만 여전히 한글로 "상태 관리"를 읽으면 '보관, 전파도 관리 맞지 않나?'라는 생각이 든다.

#### [원인 파악]

해당 서비스는 loading.tsx(Next.js의 예약어) 없이 스켈레톤과 Loader 컴포넌트로만 fallback하고 있었다. 그래서 하위 컴포넌트가 suspend하면 이를 받아줄 Suspense 경계가 없어 루트까지 올라가고, 그동안 커밋 없이 render 재시도가 반복되다가 카운터가 임계치를 넘어 React 방어 에러가 발생했다.  

```jsx
// 경계가 없을 때
<RootLayout> // suspend 전달됨
  ㄴ<DefaultLayout> // 경계 밖 (헤더)
	ㄴ<ApplicantManageLayout> // 그릴 수 있음 (LNB)
		ㄴ<Page> // suspend (콘텐츠 - 아직 준비 안 됨)
```

ApplicantManageLayout은 layout까지는 계산이 끝났지만 트리 전체가 완성되지 않았기 때문에 커밋이 막히고 있다. 아래와 같은 구조로 loading.tsx가 들어가면 Page 자리를 fallback 컴포넌트로 채워 트리가 완성되므로, 커밋이 진행된다. 


#### [개선?]

```
// 폴더 구조

src/app/
  layout.tsx            # RootLayout (Providers, cookies())
  applicant-manage/
    layout.tsx          # DefaultLayout (헤더)
    (active)/
      layout.tsx        # ApplicantManageLayout (LNB + 리스트 await) — 이동 시 유지됨
      recruit/
        [recIdx]/
          loading.tsx   # 바뀌는 세그먼트 안에 둔다
          page.tsx
```

```jsx
// 경계가 있을 때
<RootLayout> // 경계 밖 (Providers, cookies())
  ㄴ<DefaultLayout> // 경계 밖 (헤더)
    ㄴ<ApplicantManageLayout> // 경계 밖 — 공고 이동 시 재렌더되지 않고 유지 (LNB 안정)
      ㄴ<Suspense fallback={<Loading/>}> // [recIdx]/loading.tsx가 만드는 경계
          ㄴ<Page> // await가 여기서 suspend → fallback으로 대체됨
```

... 이렇게 loading.tsx로 콘텐츠 영역인 Page에 대한 fallback 컴포넌트를 제공했으나 의도치않게 페이지 깜빡임 이슈가 심해졌다😓. 


#### [개선 실패 원인]

Page에서는 아래와 같은 세 가지의 로딩 소스를 처리해야하는데,

1. page RSC 대기 : loading.tsx에서 suspend를 받아 해결함
2. react-query 데이터 : suspend가 노출되지 않지만 isLoading으로 fallback 역할 컴포넌트를 개별 사용중 (스켈레톤, loader UI)
3. Icon : 디자인 시스템에서 dynamic import로 제공하기 때문에 Icon 컴포넌트는 전부 lazy loading으로, loading.tsx 경계까지 suspend가 올라간다. 

Suspense 상위 경계를 추가하자 각각 처리하는 층과 타이밍이 다른 것이 더 부각되었기 때문이다. 페이지 단위와 lazy component단위의 경계층을 더 쌓는 테스트가 필요하다. 


#### [깜빡거리는 현상 순서]

```
LNB 항목 클릭
- page RSC 대기로 suspend : loading.tsx fallback 표시 (로딩중1 ✨)
- RSC 도착 -> page 커밋 -> 콘텐츠 layout 보임
- react-query의 data 대기로 isLoading -> Item 컴포넌트 대신 스켈레톤 UI 표시 (로딩중2 ✨)
- 데이터 도착 -> 상태 업데이트 -> Item 컴포넌트들 렌더 시작
- Item 안의 lazy Icon chunk가 아직 없음 : suspend : loading.tsx fallback 표시 (다시 로딩중1 ✨)
- Icon chunk 도착 : 깜빡깜빡 후 ... 콘텐츠 복귀
```

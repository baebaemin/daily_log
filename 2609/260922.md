### [HTTP] SSE: Server-Sent Events
HTTP 연결 하나를 끊지 않고 열어둔 채 서버가 데이터를 여러 번 밀어 보내는 방식 (ai model 답변이 한 글자씩 타이핑되듯 나오는 것처럼)

* JSON 호출 
	* 요청 1번에 응답 1번. 응답 받으면 연결이 끊어진다.
	* 요청 헤더 : Content-Type: application/json
* SSE 호출 
	* 요청 1번에 응답이 여러 조각으로 이어짐. 
	* 서버가 닫히거나 클라이언트가 닫을 때까지 유지되며, 연결이 열려 있는 동안 실시간이다.
	* 요청 헤더 : Accept: text/event-stream (서버에 스트림 응답을 요청)
	* 응답 헤더 : Conent-Type: text/event-stream (이 헤더가 있어야 SSE)

	[참고]
	- Accept: 클라이언트가 "이런 형식으로 주면 받을 수 있다"고 알리는 요청 헤더. 서버가 무시해도 프로토콜 위반은 아니다.
	- Content-Type: "지금 보내는 본문은 이 형식이다"라고 선언하는 헤더. 요청, 응답 둘 다 붙을 수 있다.

장점
- 폴링이 없다. 끝나는 즉시 알 수 있다.
- 중간 상태를 받을 수 있다. 
- 웹 방식과 달리 콜백 수신 엔드포인트가 필요 없다.

단점
- 동시 사용자 수만큼 연결이 쌓인다
- 게이트웨이, 로드밸런서, 프록시 등 유휴 타임아웃이 있으면 중간에 끊긴다. 끊기면 나머지를 받기 위해 폴링으로 복구해야 한다.
- Next.js 같은 서버리스/엣지 환경이나 일반적인 요청-응답 프레임워크에서 장시간 연결은 다루기 까다롭다.

### [Architecture] 대화형 에이전트에서 LAB-BE 간 데이터 흐름
대화형 에이전트 기능을 개발하고 있다. DB를 주관하는 BE, 에이전트 응답과 품질을 주관하는 LAB, 사용자 액션 처리와 응답을 사용하는 FE가 모여 리뷰회의를 했는데 LAB-BE 간 어떤 데이터 처리가 오가는지 이번에 알게 되었다.

* LAB은 DB에 직접 접근하지 않고 BE가 만든 대화 저장, 조회, 최근 목록, 제목 변경 등의 API를 호출한다. LAB도 API 소비자인 것.
* 대화 내용은 LAB이 들고 있지 않고, 요청마다 BE의 최근 목록 API로 읽어 LLM에 넣는다. 최근 대화 목록 API가 있어야 앞 대화를 알아들음 (ex. 사용자가 "아, 그거 말고."를 입력했을 경우 앞에서 어떤 대화가 오고갔는지를 알아야 함)
* 선택지 버튼 UI가 있는데, FE에서 { message_id, revision: 몇 번째 갱신본인지, block_id: 어떤 선택지인지 }를 전달하면  LAB은 BE의 메시지 단건 조회 API로 어떤 버튼이었는지 찾는다. 
* 존재하는 방인지, agent_type이 유효한 값인지, 요청자가 권한이 있는지도 매 턴마다 BE쪽에 확인한다.

### [HTTP] POST와 PUT
둘 다 서버에 데이터를 보내는 HTTP 메서드지만, 어디에 놓을지를 누가 정하느냐가 다르다.

POST
- 이 컬렉션에 새 자원을 만들어달라는 뜻
- 자원의 위치는 서버가 정한다.
- 요청 경로: POST /messages
- 같은 요청을 두 번 보내면 보통 두 개가 생긴다
- 멱등성: 없음

PUT
* 이 주소에 이 자원을 놓아달라는 뜻
* 자원의 위치는 클라이언트가 URL에 지정한다.
* 요청 경로: PUT /messages/abc_23809
* 같은 요청을 두 번 보내면 해당 주소에 덮어쓰므로 하나만 있다.
* 멱등성: 있음

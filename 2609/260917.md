### [Next.js] dynamic import가 만드는 청크 요청

- 청크 요청 : 브라우저가 서버에 JS 파일을 따로 요청하는 것.

- `import()`는 "필요할 때 따로 받아와라"는 뜻이라, 빌드 시점에 그 모듈이 메인 번들에서 분리돼 독립된 JS 파일이 된다. webpack은 이렇게 쪼개진 파일을 청크라고 부른다.

```jsx
import dynamic from "next/dynamic";

const iconImportList = {
    FilledIcon: dynamic(() => import(".../filled-icon.svg")),
    (...)
};
```

```
// 화면에 아이콘이 처음 그려지는 순간, 브라우저가 그 청크를 받으러 간다
GET .../_next/static/chunks/246.6f0a52c0a74f7ab2.js
```

### [HTTP] 주소가 내용을 식별하면 캐시를 비울 일이 없다

- 실제 파일 주소
  `https://{assets-주소}.co.kr/build/{app-배포환경}/(...)/710e448d4f9.../_next/static/chunks/webpack-288579f0aeb9f395.js`
    - `710e448d4f9...` : 배포 경로에 들어간 커밋 SHA
    - `webpack-288579f0aeb9f395.js` : 파일명에 들어간 webpack 콘텐츠 해시
    - 둘 다 "내용이 바뀌면 주소가 바뀐다"를 보장한다.

- 응답 헤더 : `cache-control: public, max-age=31536000, immutable`
    - `max-age=31536000` : 1년 동안 캐시해도 된다.
    - `immutable` : 이 URL의 내용은 절대 바뀌지 않으니 다시 확인할 필요 없다. (`immutable`이 없어도 `max-age`가 남아 있는 동안에는 재검증 요청을 보내지 않음)

- 주소에 콘텐츠 해시를 포함시켜 배포마다 새 URL을 만드는 방식(cache busting)에서는 캐시 무효화(purge)가 필요 없다. `immutable` 자체가 아니라 주소가 내용을 식별하기 때문인데, 이전에는 배포할 때 CDN 캐시를 비워야 했다. 하지만 지금 시스템으로는 내용이 바뀌면 새 주소로 올라가니 옛 주소의 캐시를 건드릴 이유가 없다. `immutable`은 거기에 재확인조차 하지 말라고 해주는 것! 이

- 이 구조 덕분에 사용자 한 명 기준으로 배포 사이클당 한 번만 번들/청크를 내려받게 된다. 그런데 다시 생각해보면 배포가 진행될 때마다 SHA값이 새로 바뀌므로, 내용이 바뀌지 않은 청크도 배포마다 새 주소가 된다. 배포단위로 캐시를 끊는 대신, 배포 간 캐시 재사용은 포기하는 트레이드오프이다.

## Today I Learned

### [Web API] history.state
history.state는 pushState(state, ...) / replaceState(state, ...)의 첫 번째 인자로, 넣은 값이 그대로 저장되는 빈 슬롯이다. 

- state는 구조적 복제(structured clone)이 가능한 값이어야 한다
    - 객체, 배열, 문자열, 숫자, Date, Map/Set 가능
    - 함수, DOM 노드, 클래스 인스턴스(메서드) 불가 (저장시 복제되므로 나중에 읽어도 원본 참조가 아님)

- 초기 엔트리의 history.state는 보통 null이다. 단, 앱/프레임워크가 replaceState로 초기 엔트리에 값을 심을 수도 있다. (외부에서 직접 URL 입력해서 들어올 경우에도 동일)

- popstate 이벤트의 event.state로도 같은 값이 넘어옴

### [Next.js] Next.js(App Router)가 넣는 history.state 값

Next는 라우터 네이게이션마다 자기 내부 데이터를 state에 싣는다. 클라이언트 네비게이션 후 콘솔에서 history.state를 찍으면 볼 수 있다. 인자로 넘기는 커스텀 값은 현재 브라우저 탭의 히스토리 엔트리에 붙는 클라이언트 UX 힌트로만 사용한다. (라우팅, 데이터 조회, 권한, 공유, 새로고침 복원, SSR에 필요한 상태는 URL 또는 서버 상태로 둔다.)

```js
{
    __NA: true, // "Next App Router가 만든 엔트리" 마커
    __PRIVATE_NEXTJS_INTERNALS_TREE: [...] // FlightRouterState (라우터 세그먼트 트리)
}
```

- __NA : popstate가 발생했을 때 Next 라우터가 "내가 만든 엔트리인지"를 판별하는 플래그 (Pages Router는 __N)
- __PRIVATE_NEXTJS_INTERNALS_TREE : 해당 히스토리 엔트리 시점의 라우터 상태 트리. private이라 앱 코드에서 읽거나 의존하면 안 된다.

#### 직접 데이터를 실어 쓰고 싶다면?
 Next App Router도 같은 `history.state` 슬롯에 내부 라우터 상태를 저장하므로 커스텀 데이터를 추가할 때는 기존 state를 덮어쓰지 않고 보존해야 한다.

```js
history.replaceState(
    { 
        ...history.state, 
        __goodbuilder: { // Next 내부 키나 다른 라이브러리랑 충돌하지 않게 namespace 지정
            ...history.state?.__goodbuilder, 
            scrollAnchor: "section-3" 
            },
        },
    "",
    location.href,
)
```

주로 데이터를 히스토리 엔트리(방문 시점)에 붙여야 하는데 URL에 넣기는 싫은 데이터가 있을 때 사용한다.

### 1. 커스텀 스크롤 / 무한스크롤 위치 복원
브라우저의 자동 스크롤 복원은 window 스크롤만 대상이라서 가상화 리스트나 내부 스크롤 컨테이너는 복원이 안 된다. 리스트 -> 상세 -> 뒤로가기 시 "몇 번째 아이템까지 로드했고 어디를 보고 있었는지"를 복원하려면 아래와 같이 작성.

```js
history.replaceState(
    { ...history.state, listRestore: { loadedPages: 3, anchorId: "worker-1042" } },
    "", location.href,
)
```
- url에 ?loadedPages=3&scroll=2841 로 전달할 수도 있겠지만... 공유할 가치가 떨어지고 URL이 너저분해짐
- sessionStorage는 탭 전역이라 "리스트 -> 상세 A -> 뒤로(리스트) -> 상세 B -> 뒤로(리스트)" 처럼 같은 리스트를 여러 번 오가면 어느 방문 시점의 값인지 구분할 수 없다. 또는 시점별 키 관리가 필요한데 이것도 너저분... 반면, history.state는 엔트리마다 독립이라 이러한 문제가 없다. 


### 2. URL이 같은 모달/레이어를 히스토리 엔트리로 만들기
사진 뷰어나 전체화면 레이어를 띄우지만 URL은 그대로여야 하는 경우가 있다. (ex. 등록 중 자격증 검색 화면을 전체로 띄우지만 URL 이동은 하지 않음) 이때, 사용자는 모바일 디바이스 뒤로가기 또는 제스처를 통해 뷰어/레이어를 닫고자 하지만 별도 처리를 하지 않으면 window.back()으로 이전 URL로 넘어가는 경우가 있다. 따라서 레이어를 열 때 쿠션 history entry를 하나 더 쌓아 뒤로가기로 뷰어/레이어를 닫게 할 수 있다.

```js
history.pushState(
    {
        ...history.state,
        __goodbuilder: {  
            ...history.state?.__goodbuilder,
            layer: "photoViewer",
        }
    },
    "",
    location.href,
)
```

- 헷갈리는 지점 : 레이어 엔트리에서 뒤로가기를 누를 때 `popstate.event.state`는 방금 빠져나온 레이어 엔트리가 아니라 돌아간 이전 엔트리의 state다. 

```
[0] /list
[1] /detail     state: 기존 상세 state
[2] /detail     state: { __goodbuilder: { layer: "photoViewer" } } // 사진 뷰어 쿠션 엔트리
```

- 여기서 사용자가 안드로이드 뒤로가기를 누른다면 브라우저는 [1]로 이동하고, 이때 발생하는 popstate의 event.state는 [1]의 state. 따라서 event.state.__goodbuilder.layer만 보고 닫을 레이어를 판단하면 안 되고, 현재 레이어가 열려 있는지는 React state/ref 등으로 별도로 알고 있어야 한다.

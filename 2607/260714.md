### [semantic-release] 유의적 버전 명세 

- 디자인 시스템 업데이트 하다가 1.4.9에서 패치 버전업을 하면 ... 1.5.0가 되나 ?? 그래도 되나 ... ?? 싶어서 찾아봤다 

- 결론 : 1.4.10로 올리면 됨 ^-^.. 

- 참고 링크 : https://semver.org/lang/ko/

- 위의 링크 FAQ가 유익해서 DS/harness 서브모듈 운영할 때 도움이 되어 몇 자 옮겨 적는다
  - 1.0.0의 기준은? 
    - 소프트웨어가 실 서비스에 쓰이기 시작했을 때
    - 사용자들이 믿고 쓰는 API가 구축되었을 때
    - 하위 버전 호환에 대해 우려하기 시작했을 때

  - 호환되지 않아서 주 버전을 매번 올리면 42.0.0이 되면 어떡해? : 그러니 호환되지 않는 변경에 대한 여파/비용/혜택을 평가하자

  - 부버전을 올렸는데 호화노디지 않는 변경이 들어갔다면? : 즉시 fix/복구해서 새 부버전을 배포한다. 단, 이미 배포된 버전을 변경해선 안된다! 

  - 내부 의존성을 바꿀 때에도 버전업 해야할까? : 공개 API가 유지된다면 주 버전 업데이트 대상은 아니다.

  - 수버전 배포에서 버그 발생하면 어떻게 할까? : 대규모 사용자층이 있다면 수정사항이 수버전 범위더라도 주버전 배포를 하는 것이 최선이다.

  - 기능을 제거할 땐? : 문서를 업데이트해서 변화를 알린다 -> 새 주버전에서 기능을 완전히 제거하기 전에, 부버전 배포를 최소한 한 번은 진행한다

### [iOS] WebView·SafariViewController·Safari의 URL 처리 차이 
버티컬 서비스 앱에서 메인 서비스와 연동, 로그인/인증/리다이렉트를 위해 외부 URL을 열어야 했다. 
세 가지 방법 모두 WebKit 계열 렌더링을 사용하더라도 URL을 여는 컨테이너 및 특성이 달라진다. 

1. `WKWebView` 
  - 앱 안에 웹 화면을 직접 띄우는 WebView
  - 주소창/탭/공유/다운로드/확장 같은 Safari 기본 기능이 없으며, 필요시 앱이 직접 구현해야 함
  - 앱의 웹 세션을 직접 제어하거나 네이티브와 웹 간 통신이 필요할 때 적합
  - (UI에 따라 다르겠지만) 사용자에게 브라우저처럼 보이지 않음

### <hr />

2. `SFSafariViewController`
  - Safari와 사실상 같은 시스템 제공 인앱 브라우저. 
  - 앱의 WKWebView와 세션/쿠키가 격리됨 - 외부 로그인/리다이렉트 처리하기 안정적
  - 사용자에게 브라우저처럼 보임 (주소 표시, 닫기 버튼 등)
  - 앱이 웹 콘텐츠를 제어한다기 보다는 시스템 브라우징 경험에 맡김

### <hr />

3. `window.open`
  - 시스템 브라우저 새 탭. 웹 환경 폴백, 완전한 브라우저

  - 로그인·리다이렉트가 많은 외부 URL은 격리된 SafariVC 계열이 안정적이다.

  - 기획에서 요구했던 새 창 UX는 SafariVC로도 충족(전체화면으로 뜨고 닫으면 앱 복귀)하므로 SFSafariViewController를 사용했다.
